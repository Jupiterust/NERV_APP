## 2. P0 — 会导致跑飞或整场归零

### F-1 ｜协议层 payload ≥ 244 字节爆栈（4 处）✅已核实

**为什么现在必须修**：赛题的 `报文长度` 字段是 **1 字节**，合法 payload 上限 255。今天最长的应答才 23 字节（`0x0103`），所以这个洞是潜伏的。**但文件读写正好是唯一会把 payload 顶到上限的功能**——TF 卡命令一上，第一帧就炸。

赛题原文：「如某一步骤导致下位机程序卡死，后续无法测评，则以此评分计」。这条一炸就是整场。

| 位置 | 缓冲区 | 实际需要 | 越界条件 |
|---|---|---|---|
| `General_Protocol.c:457` | `uint8_t raw_buf[256]` | `13 + payload_len` | payload ≥ 244 |
| `General_Protocol.c:487` | `char ascii_tx_buf[512]` | `2 × (13 + payload_len)` | payload ≥ 244 |
| `General_Protocol.c:412` | `uint8_t raw_frame[256]` | `ascii_frame_len / 2` | 收到 > 512 字符的帧 |
| `General_Protocol.c:23` | `HexStrToBytes()` | — | **无 out_size 参数，完全不检查边界** |

接收侧最严重：`rx_buffer` 是 1024 字节（`General_Protocol.c:5`），`HexStrToBytes()` 会把 `ascii_frame_len/2` 字节无条件写进 `raw_frame[256]`，最多能踩 256 字节的栈。而且注意——**一个 payload=255 的完全合法帧（268 字节 → 536 ASCII 字符）现在就已经溢出 12 字节**，不需要恶意构造。

**修法**：

```
raw_buf[256]      → raw_buf[288]
raw_frame[256]    → raw_frame[288]
ascii_tx_buf[512] → ascii_tx_buf[600]
HexStrToBytes(hex_str, str_len, out_bytes)
                  → HexStrToBytes(hex_str, str_len, out_bytes, out_size)
                    超限返回 -1，走现有的"帧长不匹配"错误应答分支
```

再在 `file_service.h` 里定一个 `FILE_CHUNK_MAX 200`，自己发的分片永远不超过它，留余量。

**验收**：
- 构造一帧 payload=255 的合法命令（`crc_tool.py` 生成），设备正常回错误应答或正常处理，不复位；
- 构造一帧 1000 字符的伪帧（`A5B6` + 992 个合法 hex 字符 + `B6A5`），设备回错误应答，不复位；
- 自己发一帧 payload=200 的应答，上位机收到的 CRC 正确。

### R-4 ｜`0x0403 / 0x0413` CH2 阈值是空函数，收到指令完全不回话 ✅已核实

`Function.c:463` `CMD_CFG_READ_THRES_CH2_FUNCTION()` 和 `Function.c:504` `CMD_CFG_WRITE_THRES_CH2_FUNCTION()` 都是空函数体（注释写着"未使用，留下接口"）。命令字在 `General_Protocol.c` 里是**正常分发**的，所以走到空函数就什么都不发。

**为什么 P0**：初赛这两条不考（CH2 是 PT100，官方说不考察）。**决赛的 CH2 就是那三路新通道之一**，这两条几乎必然被激活。而且"不回话"在测评员那边和死机没区别——比回一个错误帧还糟。

**修法**：照 `CMD_CFG_READ_THRES_CH0_FUNCTION` / `CMD_CFG_WRITE_THRES_CH0_FUNCTION` 抄，阈值存到 `Data_class_structure` 新增字段（**只能追加，见 §0**）+ `param_handle` 新槽位（`bsp_flash_param_t.val_f[5]` 现在只用了 4 个，还有 1 个空位；若三路都要阈值需要扩数组）。

**验收**：清单 X-01 / X-02 两行的"预期应答"从"无应答"改成正常应答，实测通过。

### F-5 ｜FatFs 只认 8.3 短名，而补救文件不在仓库、现场禁网 ⚠️部分推测

**事实**：`FatFt/ffconf.h:93` 是 `_USE_LFN 0`，所以**写入只支持 8.3 短文件名**。`bsp_sdio_resolve_path()` / `bsp_sdio_fw_find()` 用扫目录反查 8.3 别名的办法解决了**读**，写没有。另外 `ffconf.h:60` 的 `_CODE_PAGE 932` 是日文 Shift-JIS，明显是抄来没改。

**风险**：现场若要求写 `sample_data.csv` 这类长名，直接失败。而开 LFN 需要 `option/ccsbcs.c`，**这个文件不在本仓库里**，决赛现场「不允许任何网络连接操作」，到时候拿不到。

**必须赛前做**（这是整份文档里最有时限性的一条）：
1. 把 `ccsbcs.c` 弄进 `FatFt/`，`_USE_LFN` 打开（1 或 2），`_CODE_PAGE` 改 `936`（简中）或 `437`；
2. 注意 LFN 会吃约 512 字节 BSS，确认 RAM 还够；
3. 编译 + 烧板 + 真卡验证长名读写；
4. **同时保留**一层"长名自动转 8.3 大写"的兜底函数，LFN 万一出问题能退回去。

**验收**：真卡上 `f_open("Sample_Data_2026.csv", FA_WRITE|FA_CREATE_ALWAYS)` 成功，拔卡插电脑文件名完整。

### R-1 ｜告警字符串里的阈值恒为 1.00 ✅已核实

`Driver/bsp_ADC.c:8-9` 定义了两个全局 `float ch0_threshold = 1.0f; float ch1_threshold = 1.0f;`，**全工程没有任何地方写过它们**。而 `Function.c:617,619` 把这两个裸变量传给告警字符串：

bsp_log_active_report_and_record("CH0", ch0_threshold, Data_class_structure.ch0_current_val);

真正的阈值走的是另一条路：`0x0411` 写进 `Data_class_structure.ch0_threshold`（`Function.c:482`），比较也用它（`Function.c:613`）。所以**判超限用的是真阈值，打印出来的永远是 1.00**。

### R-7 ｜广播帧的错误应答用 `FFFF` 当源 ID ✅已核实

`Protocol_HandleFrame()` 里五处错误应答用的是**收到的** `device_id`：`General_Protocol.c:101, 109, 357, 361, 374`。上位机若用广播地址 `FFFF` 发一条非法命令字（K-03 完全可能这么测），设备回出去的帧源 ID 就是 `FFFF`——而 `FFFF` 是广播地址，不是合法设备地址。

对比：`Protocol_ParseChar()` 里的三处（`436, 439, 442`）用的是 `MY_DEVICE_ID`，是对的。**修法**：五处统一改成 `MY_DEVICE_ID`。

### R-8 ｜自动上报期间仍应答异常帧 ✅已核实

H-02 是**扣分项**：「除停止自动上报外，其他应答扣分」。

现在的门禁在 `General_Protocol.c:116`（`Regular_reporting_Flag == 1` 时只放行 `0x0303`），但它位于 `Protocol_HandleFrame()` 内部，而这三类错误应答在它**之前**就发出去了：

- `General_Protocol.c:436/439/442` — 在 `Protocol_ParseChar()` 里，压根不经过 `HandleFrame`
- `General_Protocol.c:101` — 帧长不匹配，在门禁之前
- `General_Protocol.c:109` — 未知帧类型，在门禁之前

**修法**：把"是否处于自动上报"抽成一个函数（例如 `Protocol_AutoReportActive()`），在这五处发错误帧之前统一判一次。注意赛题 4.5.7(2) 要求未知帧类型「丢弃该帧，**记录日志**，返回错误应答」——自动上报期间可以只记日志不回帧，`oplog_add()` 已经现成。

### F-4 ｜TF 卡零协议暴露 + 缺二进制追加写 ✅已核实

**好消息**：驱动层很全（`Driver/bsp_sdio.h:100-231`）——覆盖写、追加写、带 offset 的二进制读、按行读、按 offset 逐行读、exists、size、delete、mkdir、rename、list_to_buf、get_space、format 都有。`get_fattime()` 也接了 RTC（`FatFt/diskio.c:242`），拔卡看文件时间戳是对的。

**缺口**：
1. **自定义协议一条文件命令都没有**。目前唯一的出口是 Modbus 的 `MB_COIL_LOG_TO_SD` 线圈（`modbus_data_map.c:536`），写一行文本。
2. **没有二进制追加写**。`bsp_sdio.h:101` 只有 `bsp_sdio_file_append_text(const char*)`，靠 NUL 结尾——二进制数据里出现 `0x00` 就截断。分片写必须要一个 `bsp_sdio_file_append(const void* data, uint32_t len)`。

⚠️**推测的考法**（详见 §9）。**建议落地形状**：

```
Function/file_service.c / .h     ← 协议无关的文件服务层
  命令字、默认文件名、分片大小、CSV 列顺序、错误码 全部是 file_service.h 里的 #define
  上层无论是自定义协议还是 Modbus，都调同一组函数
```

先自己定一版分片协议（现场给了别的就只改解包层）：
- 读：`文件名(N) + offset(4) + len(1)` → 应答 `实际长度(1) + 数据(N)`
- 写：`文件名(N) + offset(4) + 数据(N)`，顺序写用 append 实现

**错误码要可区分**：无卡 / 文件不存在 / 空间不足 / 文件名非法 / 越界读，各回不同内容。⚠️初赛专门有 K 组考异常帧，决赛很可能照抄这个思路考 TF 卡异常（**不插卡时下发写命令**是最可能的一条）。

### F-10 ｜FreeModbus"用库"的说法要能自圆其说

决赛样题原文：「**利用 Free Modbus 库**完成 Modbus 从站开发」。

现状：`mb.c` / `mbrtu.c` / `mbascii.c` / `port/portserial.c` / `porttimer.c` / `portevent.c` 全部 `IncludeInBuild=0`，只用了 `functions/mbfunc*.c` + `port/port.c` + `rtu/mbcrc.c`。

技术上这个决策是对的（那套引擎要独占 USART1 的 RX 中断，和 `bsp_rs485.c` 的 ISR 撞 `USART1_IRQHandler` 重复符号；且它调的 `my_usart1_init()` 等三个函数本仓库根本没实现）。**但评委翻工程文件看到一半库文件被排除，这条是可以被挑的。**

**待办（文档/答辩，不是代码）**：写一段话，把它包装成**移植层替换**而非绕过——"保留 FreeModbus 的功能码层与寄存器回调层，替换其串口/定时器移植层，以适配基于 TIM6 硬件定时器的 T3.5 帧界定"。**赛前不要试图去恢复那套引擎**，会引入新 bug。

### F-11 ｜Modbus 点表重叠只能手工查

`MB_CHK` 只查越界不查重叠。现场按官方点表重排地址后，**必须手工对一遍** float（2 寄存器）和 scaled（1 寄存器）有没有撞上——撞了两个写都执行、后写的赢，编译和运行都不报错。

**可选改进**：写个小 Python 脚本读 `modbus_data_map.h` 的 `#define` 算重叠，赛前放进 `文档/`。

### F-12 ｜SD 单次写耗时未实测

`f_open + f_write + f_close` 一轮在 SDIO 4bit + DMA 下大概几十毫秒，赶上 FAT 表更新更久。这段在主循环里是阻塞的——不会破坏接收（RS485 是中断 + 1024 字节缓冲），但会**把 Modbus 应答拖过主站超时**。

**待办**：实测。超过 100ms 就改成"文件常开 + 定期 `f_sync()`"。

### F-13 ｜掉电安全

记录过程中每 N 条 `f_sync()`；`0x0101` 重启和 `0x03AA` 睡眠前先 `f_close()`。
