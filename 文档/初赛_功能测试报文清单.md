## 一、怎么用

**串口设置**：19200 / 8 / N / 1，RS485 接 USART1。

**关键一点：这是 ASCII 文本协议，不是二进制协议。**
表里 `A5B60001010101000215ABB6A5` 这一串，要在串口工具里以**文本/字符串**方式发送，实际线上跑的是
`'A'`、`'5'`、`'B'`、`'6'`… 这 26 个 ASCII 字符。如果串口工具勾了 "HEX 发送"，就会发出 13 个二进制字节，
设备收不到帧头，**不会有任何反应**。

- 大小写：解析函数 `CharToHex()` 大小写都收，设备回复统一用大写。
- 不要加换行、空格、`0x` 前缀。
- 帧尾 `B6A5` 一到就立刻解析，所以可以连续粘贴多条，中间不用等。

**帧结构速查**（本文表格里的报文都按这个顺序拼）：

```
A5B6 | 设备ID(2) | 帧类型(1) | 命令字(2) | 报文长度(1) | 版本(1) | 内容(N) | CRC16(2) | B6A5
                                          ↑只算内容N     ↑固定02              ↑大端,高字节在前
CRC16-Modbus 计算范围 = 从 A5B6 到内容末尾（不含 CRC 和 B6A5）
```

**帧类型**：`01` 上位机下发 / `02` 设备应答 / `05` 心跳 / `FF` 错误或告警。
**默认设备 ID**：`0001`。表中除特别标注外都用 `0001`。

**协议路由**：`Protocol_mode` 默认 4（自动嗅探），首 4 字节是 ASCII `"A5B6"` 就走自定义协议，
其余走 Modbus。本清单所有帧都以 `A5B6` 开头，不受 Modbus 共存逻辑影响。

## 二、建议测试顺序

破坏性测试排最后，避免一步做错导致后面全测不了：

1. **A → B → C → D → E → G**：上线、只读查询、时间、变比、阈值、DAC 联动（全部无副作用，可反复做）
2. **F**：重启持久化（会重启，但参数不丢）
3. **H → I → J**：自动上报、告警、睡眠
4. **K**：异常帧（无副作用）
5. **L**：改设备 ID —— **测完必须用 L-03 改回 0001**
6. **M**：改波特率 —— **破坏性，测完必须用 M-03 改回 19200**
7. **O**：恢复出厂设置 —— **破坏性，会清掉全部参数并复位**（正好能把 ID / 波特率一把拉回默认）
8. **N**：Bootloader / OTA —— **破坏性，会覆盖 APP，放最后**

> ⚠️ 文档特别提示：波特率和 Bootloader 是破坏性测试；改完波特率通不了信，后续测评不计分。
> 出厂默认必须是 **19200**，自动评测启动时上位机会强制切到 19200。

| G-01f | 回读 CH1 | `A5B600010102020002515BB6A5` | `A5B6 0001 02 0202 04 02 <≈1.65×变比> <CRC> B6A5` | **必须 ≈1.65V**。若读到 ≈2.05V，说明 R-0 的 bug 又回来了 |

> **只测 `0FFF` 和 `0000` 验不出 DAC 的问题**：这两个端点在 R-0 那个 bug 下恰好也是对的。
> 判别性的是中间值和高段值，即 G-01e~G-01g。DAC 码值 → 理论电压对照：
>
> | 码值 | 十六进制 | 完整报文 | 理论输出 |
> |---|---|---|---|
> | 0 | `0000` | `A5B6000101030102020000A5BEB6A5` | 0.000 V |
> | 2048 | `0800` | `A5B600010103010202080065B9B6A5` | 1.650 V |
> | 3300 | `0CE4` | `A5B6000101030102020CE4EEBBB6A5` | 2.659 V |
> | 3500 | `0DAC` | `A5B6000101030102020DAC48BAB6A5` | 2.821 V |
> | 4095 | `0FFF` | `A5B6000101030102020FFF15FBB6A5` | 3.300 V |
>
> 注意 `bsp_dac_init()` 开了输出缓冲（`dac_output_buffer_enable`），GD32 的 DAC 缓冲达不到轨到轨，
> 码值 0 实测约 0.1~0.2V、满量程约 3.1V。两个端点对不上理论值是**正常的硬件特性**，不是 bug；
> 中间段的线性度才是判据。

> `2` = 放行但不回应答（间隔照改，总线上不多发字节，H-02 抠不到，代价是收不到确认）。
> 分发器里的放行名单在 `General_Protocol.c` 的自动上报门禁处，跟着这个宏走。

## 四、测试中发现的代码问题（建议赛前修）

对照文档逐条核代码时发现下面几处，按影响排序。**R-0 已修复，其余待处理。**

### R-0 ｜DAC 把码值当毫伏用 —— 影响 G-01（2 分）｜✅ 已修复

**现象**：`Function.c` 的 `CMD_CTRL_SET_DAC_VOLT_FUNCTION()` 原本把协议载荷交给
`bsp_dac_set_voltage()`：

```c
uint16_t target_mv = ((uint16_t)DATA_ARRAY[0] << 8) | ((uint16_t)DATA_ARRAY[1]);
bsp_dac_set_voltage(target_mv);          // ← 这个函数的入参单位是毫伏
```

而 `Driver/bsp_DAC.c:23` 的实现是：

```c
void bsp_dac_set_voltage(uint16_t voltage_mv) {
    if (voltage_mv > BSP_DAC_VREF_MV) voltage_mv = BSP_DAC_VREF_MV;   // 3300 限幅
    uint16_t dac_val = (uint32_t)voltage_mv * 4095 / BSP_DAC_VREF_MV; // mV → 码值
```

但赛题 4.5.3(1) 写的是"下发内容：**0~4095 的一个值**，转换为 16 进制 `0000~0FFF`" ——
这是 12 位 DAC 原始码值，不是毫伏（若是毫伏，上限该写 `0x0CE4`=3300 而不是 `0x0FFF`）。
码值被当成毫伏又转了一次，实际写进 DAC 的是 `min(N,3300) × 4095/3300`，
等效于**把码值直接当毫伏输出**：

| 下发码值 | 应输出 | 修复前实际 | |
|---|---|---|---|
| `0000` (0) | 0 V | 0 V | ✅ 端点巧合正确 |
| `0800` (2048) | 1.650 V | **2.048 V** | ❌ 偏大 1.24 倍 |
| `0CE4` (3300) | 2.659 V | **3.300 V** | ❌ |
| `0D00`~`0FFE` | 2.67~3.30 V | **全部 3.300 V** | ❌ 高端 19% 量程压成一条直线 |
| `0FFF` (4095) | 3.300 V | 3.300 V | ✅ 端点巧合正确 |

两个端点恰好正确、中间全错，所以**只拿 `0FFF`/`0000` 测会误判为正常**。

**影响面**：不只是 G-01。D-00 是 CH1 全部测试的信号源，B-05、D-02（CH1 变比）、
H-01（自动上报里的 CH1 字段）的数值判读都会跟着偏。

**修复**：驱动里本来就有正确的 `bsp_dac_set_raw()`（`bsp_DAC.c:38`，限幅 4095、直写寄存器），
改为调它即可。已改，`Function.c`：

```c
uint16_t dac_code = 0;
dac_code = ((uint16_t)DATA_ARRAY[0] << 8) | ((uint16_t)DATA_ARRAY[1]);
bsp_dac_set_raw(dac_code);
```

`bsp_dac.h` 由 `bsp_sys.h:80` 引入，声明本来就可见，无需改 include。
**回归验证**：跑 G-01e~G-01g，中间值和高段值必须落在理论电压上。

### R-1 ｜告警字符串里的"阈值"永远是 1.00 —— 影响 I-02（2 分）

`Function/Function.c:468` / `:470`：

```c
bsp_log_active_report_and_record("CH0", ch0_threshold, Data_class_structure.ch0_current_val);
```

这里的 `ch0_threshold` 不是结构体成员，而是 `Driver/bsp_ADC.c:8` 里的一个同名全局：

```c
float ch0_threshold = 1.0f;   // 全工程只有这一处赋值，从未被更新
float ch1_threshold = 1.0f;
```

判超限用的是 `Data_class_structure.ch0_threshold`（正确），但**打印和存 flash 的阈值字段取的是那个恒为
1.0f 的全局**。所以不管把阈值设成多少，告警字符串里第三段永远是 `1.00`。
文档要求格式是 `时间|通道|阈值|实际值`，阈值对不上很可能判不通过。

修法：两处 `ch0_threshold` → `Data_class_structure.ch0_threshold`，`ch1_threshold` 同理。

### R-2 ｜告警字符串分隔符不统一 —— 影响 I-02 / I-03d

同一份数据存在三种格式：

| 位置 | 格式串 | 结果 |
|---|---|---|
| `Log_recording_function.c:107` `bsp_log_record_alarm()`（主动模式存 flash） | `"%s \| %s \| %.2f \| %.2f"` | 竖线**两边有空格** |
| `Log_recording_function.c:144` `bsp_log_active_report_and_record()`（主动模式发串口） | `"%s\|%s\|%.2f\|%.2f\r\n"` | 竖线**两边无空格** |
| `Log_recording_function.c:202` `bsp_log_record_only()`（被动模式存 flash） | `"%s\|%s\|%.2f\|%.2f"` | 竖线**两边无空格** |

文档示例是 **有空格** 的：`2026-01-01 12:00:00 | CH0 | 10.50 | 11.12`。
于是 I-02（主动上报，走串口，无空格）和 I-03d（查询记录，主动模式那条有空格、被动模式那条无空格）
会输出两种样式。如果上位机是严格匹配，两边都有风险。建议统一成文档样式（带空格）。

### R-3 ｜短于 13 字节的帧被静默丢弃，不回错误帧 —— 可能影响 K-02（2 分）

`General_Protocol.c:366`：

```c
for (int16_t i = 0; i <= rx_index - 26; i++) {   // 最小 ASCII 帧长 26
```

收到帧尾时如果整个缓冲区不足 26 个 ASCII 字符（即整帧 < 13 字节），这个循环一次都不进，
`start_idx` 保持 -1，函数直接清空缓冲区返回，**一个字节都不回**。
下面那段 `raw_len < 13 → 回错误帧` 的代码因此永远走不到。

评分项 K-02 是"长度错误帧 → 返回错误应答报文"。如果评测端发的是**截断帧**而不是
"长度字段写错的完整帧"，当前固件会 0 分（对应本清单 K-02c）。
表里 K-02a / K-02b 那两条（帧完整、长度字段不符）是能正常回错误帧的。

保险做法：把最小长度判断从帧头搜索里拆出来，帧尾一到就先按 `raw_len < 13` 回一帧错误应答。

### R-4 ｜0x0403 / 0x0413（CH2 阈值）是空函数，收到指令完全不回

`Function.c:327` `CMD_CFG_READ_THRES_CH2_FUNCTION()` 和 `:368` `CMD_CFG_WRITE_THRES_CH2_FUNCTION()`
都是空的（只有注释"未使用，留下接口"），但 `General_Protocol.c` 里有 `case` 会派发过去。
结果是：命令被"接住"了却不产生任何应答，上位机只能等超时。

3.4 评分表里确实没有 CH2 阈值项，所以不影响得分；但文档 4.3 命令字表列了这两条。
最低成本的兜底：让它们至少回一帧错误应答，别让上位机干等。

### R-5 ｜0x0503（执行升级流程）在 APP 里是空函数

`Function.c:402` `CMD_OTA_EXECUTE_FUNCTION()` 是空的。
实际流程上 0x0501 会重启进 Bootloader，0x0502 / 0x0503 由 Bootloader 工程应答，所以正常测评路径不受影响。
但如果上位机在 APP 运行期间发 0x0503，APP 不回任何东西。**确认 Bootloader 工程里这两条实现完整**再上场。

### R-6 ｜0x0221 返回的是电压不是温度

`Function.c:193`：

```c
Data_class_structure.ch2_current_temp = ad3344_get_ain0_volt();
```

`ad3344_get_ain0_volt()`（`Driver/bsp_GD30AD3344.c:390`）返回的是 AIN0 电压值，没做 PT100 阻值→温度换算。
文档 4.5.2(2) 写的是"温度值对应的 IEEE 754 单精度浮点数"。
不在评分表里，但文档答辩/技术文档环节可能被问到。

### R-7 ｜广播帧出错时，错误应答会用 FFFF 作为源 ID

`General_Protocol.c:102` / `:110` 在长度错误、帧类型错误时用的是**帧里带的** `device_id` 回复：

```c
Protocol_SendFrame(device_id, TYPE_ERROR, CMD_SPEC_ERROR_REPLY, NULL, 0);
```

如果收到的是广播帧（`FFFF`）且长度不对，回出去的错误帧源 ID 就是 `FFFF`，而不是设备真实 ID。
`Protocol_ParseChar()` 里的 CRC 错误分支用的是 `MY_DEVICE_ID`（正确）。建议统一成 `MY_DEVICE_ID`。

### R-8 ｜自动上报期间，长度/帧类型错误帧仍会应答 —— H-02 扣分项

`Protocol_HandleFrame()` 的检查顺序是：版本 → ID → **长度 → 帧类型** → 自动上报门禁 → 命令分发。
长度错和帧类型错的两处错误应答排在自动上报门禁**前面**，所以自动上报期间收到畸形帧仍会回一帧。
H-02 的判据是"除停止自动上报外，其他应答扣分"。评测大概率只发正常命令，风险不高，
但把自动上报门禁提到长度检查之前更稳妥。

### R-9 ｜设置时间失败时不应答 —— 影响 C-01（2 分）

`Function.c:77`：

```c
if(bsp_rtc_set_unix_timestamp(received_ts, 0) == SUCCESS) { ...回 OK... }
```

RTC 写失败时没有 `else`，一个字节都不回，上位机只能超时重发 2 次后判失败。
建议失败时回一帧错误应答，至少让现象可见。

### R-10 ｜设上报间隔会凭空多发一帧自动上报 —— 影响 H-00 / 整个 H 组｜✅ 已修复

**实测现象**（2026-08-06，自动上报**从未开启**的情况下）：下发一条 `0x0261`，收回来是两帧粘在一起。

```
TX：A5B600010102610102037E1FB6A5
RX：A5B600010202610102FF0C1FB6A5          ← 第 1 帧：0x0261 的 OK 应答，正确
    A5B600010203020C026A741E4C3FDF02BD3F7DF4AC91E4B6A5   ← 第 2 帧：0x0302 自动上报数据，不该有
```

判定依据：帧里的时间戳跟每次下发命令的墙钟时刻严丝合缝（`…4C`→`4D`→`4E`→`54`→`5D`），
而两次命令之间空闲 5.7 秒内**一帧都没有** —— 说明不是定时器在跑，是**一条命令触发一帧**。

**根因**：`bsp_tim7_set_timeout()` 里改 ARR 必须靠 `timer_event_software_generate(UPG)`
重新装载，但软件更新事件和真正的计数溢出**完全等价**，一样置 UIF；而 TIM7 的更新中断
从 `bsp_tim7_init()` 起就一直使能（那里只 `timer_disable()` 停了计数器，**停计数器并不阻止
软件更新事件**）。于是中断被触发 → `g_report_flag = 1` → 主循环发一帧 `0x0302`。
原来那句事后 `timer_flag_clear()` 清晚了：中断优先级 (2,3) 高于主循环，事件产生的当场
CPU 就进 ISR 了，标志早被 ISR 清掉、`g_report_flag` 已经置起来了。

**扣分风险**：H-00a/b/c 的期望应答是单独一帧。多出来的那帧轻则判"应答不符"，重则被评测
软件当成下一条命令的应答，导致 H 组后续测试项连锁失败。

**修法（两处，都已改）**：
1. `Driver/bsp_general_timer.c: bsp_tim7_set_timeout()` —— 产生 UPG 事件前先
   `timer_interrupt_disable(TIMER7, TIMER_INT_UP)`，装载完清标志再使能，并顺手清 `g_report_flag`。
2. `User/main.c` 主循环 —— 发上报帧前增加 `Data_class_structure.Regular_reporting_Flag == 1`
   判断。`g_report_flag` 只代表"更新中断来过一次"，不代表"用户开启了自动上报"；没有这层
   兜底时设备会一边发数据帧、一边在 OLED 和输入寄存器 `MB_IREG_AUTO_FLAG` 里自称"未上报"。

## 五、附录 · CRC 计算与改报文

改载荷（换时间戳、换阈值、换 ID…）后 CRC 必须重算。把下面存成 `crc_tool.py`：

```python
# -*- coding: utf-8 -*-
import struct, sys

def crc16_modbus(b):
    crc = 0xFFFF
    for x in b:
        crc ^= x
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc

def frame(dev_id, ftype, cmd, payload=b''):
    """按协议拼一帧，返回可直接粘进串口工具的 ASCII 字符串"""
    body = struct.pack('>HHBHBB', 0xA5B6, dev_id, ftype, cmd, len(payload), 0x02) + payload
    return (body + struct.pack('>HH', crc16_modbus(body), 0xB6A5)).hex().upper()

def f32(v):
    """float -> IEEE754 大端 4 字节"""
    return struct.pack('>f', v)

if __name__ == '__main__':
    # 例：设 CH0 阈值 = 12.75
    print(frame(0x0001, 0x01, 0x0411, f32(12.75)))
    # 例：设时间为某个 UTC 秒数
    print(frame(0x0001, 0x01, 0x0105, struct.pack('>I', 1785931200)))
    # 例：设 DAC = 3000
    print(frame(0x0001, 0x01, 0x0301, struct.pack('>H', 3000)))
    # 例：查询任意命令字
    print(frame(0x0001, 0x01, 0x0201))
```

**常用浮点数速查**（IEEE754 大端）：

| 数值 | 十六进制 | 数值 | 十六进制 |
|---|---|---|---|
| 0.5 | `3F000000` | 2.5 | `40200000` |
| 1.0 | `3F800000` | 3.0 | `40400000` |
| 1.5 | `3FC00000` | 3.5 | `40600000` |
| 2.0 | `40000000` | 10.5 | `41280000` |
| 21.59 | `41ACB852` | 100.0 | `42C80000` |

**手算 CRC 的验证锚点**：文档里 `A5B6 0001 01 0101 00 02` 的 CRC 是 `15AB`，
高字节 `15` 在前。若你的工具算出 `AB15`，说明字节序反了 —— 本协议是**大端**，
和标准 Modbus RTU 的小端 CRC 相反。
